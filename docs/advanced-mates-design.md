# 高级配合：比例 / 齿轮（实现方案）

> 状态：**方案已定，未实现**。这两类配合与「刚体夹具」式的标准配合本质不同，必须换一条实现路线，本文把那条路线钉死，避免下一轮又从头推。

## 1. 为什么不能用现有那条路

现有标准配合（重合/平行/垂直/距离/角度/限制）全都实现成**一副虚拟刚体夹具**：
把几何摆好（`MateFrames.Plan`：frame1/frame2 的局部位置与朝向）、把不用动的自由度锁掉、
把「真需要数值」的那条轴交给 `setLimit`，然后交给约束求解器。这条路的隐含前提是
**两个结构之间的相对位姿是固定的**（或只有一条自由度被区间限制），所以「值 = 几何」。

比例与齿轮违反这个前提：

* **比例**：`d_i = k_i · d_1`（基准面与第 i 个面之间的距离 = 比例 × 第一条距离）。
  这里的相对位姿**随驱动器连续变化**，不是「一副摆好的夹具」。
* **齿轮**：`Δθ_B = −(z_A / z_B) · Δθ_A`，两个自转轴之间的**角速度比**是常数。
  它约束的是「速度/增量」，不是「位姿」—— 一副夹具无法表达速度比。

在 SolidWorks 里两者都是**运动副/耦合**（mate 之外的 mechanism），我们也必须做同样的区分：
它们是**每个物理子步都参与的运动学辅助（kinematic assist）**，而不是一次算好的关节。

## 2. 统一的实现路线：子步辅助

两者共用同一套基础设施（建议放 `com.ovo.sablestopnow.kinematic`）：

```
每物理子步（挂在 SubLevelPhysicsSystemMixin → MateRegistry.physicsTick 这条链上）：
  1. 测量：从当前 logicalPose() 现算驱动量（比例=驱动器距离 d1；齿轮=驱动轴转角 θ_A）
  2. 求目标：按规则算出从动量（d_i = k_i·d1；θ_B = θ_B0 − ratio·(θ_A − θ_A0)）
  3. 限速修正：把从动结构朝目标「挪一小步」（位置沿测量轴 / 朝向按 slerp），
     每子步清零它的线速度（或角速度），并登记超速锁豁免（MateRegistry.markMateMoved）
```

第 3 步与既有的两种「缓慢搬运」是**同一套纪律**（`MateRegistry.startSnap` 的限速 + 每子步清速度、
`ModelMoveService` 的绝对目标插值）：限速保证不会把一段位移灌成动量，清速度保证不会攒出「虚空动能」。
**这就是用户说的「幽灵物体只传递力、没有质量」在速度层面的对应做法。**

### 2.1 比例（Ratio）

* 选择：`≥ 3` 个面；**最后选择的那个是基准（driver）**，其余为从动。
* 存储：`k_i = d_i⁰ / d_1⁰`（创建时按初始距离自动算出；`d_1⁰` 为 0 时该条跳过并提示）。
  每个 `k_i` **可单独编辑**（左侧列表：一行一个面 + 一个数字框）。
* 驱动量 `d_1`：基准面 ↔ 第 1 个从动面之间的**有向距离**（沿该对的面法线测量，沿用
  `MateFrames.distanceAxis` 的规则）。
* 从动：每个从动结构沿它自己的测量轴挪到 `k_i · d_1`，限速 + 清速度。
* 基准结构本身**不受约束**（用户要的就是「基准面自由移动时按 k 联动」）。

### 2.2 齿轮（Gear）

* 选择：按顺序 4 条线段 —— **固定轴A、齿轮轴A、固定轴B、齿轮轴B**（`ModelTools.GEAR` 的 `maxRefs = 4`）。
* 语义（已与用户确认）：
  * **齿轮轴 = 该齿轮的自转轴**（A 的齿轮绕齿轮轴A 自转）；
  * **固定轴 = 该齿轮所在机身/世界的参考轴**（用来定基准与反向）；
  * **传动比由玩家手填齿数比** `z_A : z_B`（四条线只用来确定轴的位置与朝向），并提供**反转**复选框。
* 驱动量：A 的转角 `θ_A` = 机身参考系里、绕齿轮轴A 的自转角（以固定轴A 定零位）。
  从动：B 绕齿轮轴B 转到 `θ_B0 − ratio·(θ_A − θ_A0)`，`ratio = z_A / z_B`（勾反转则整体取反）。
* 修正方式：只改**绕该轴的角**，用 `handle.teleport(保持不变的位置, slerp 后的朝向)` +
  清零角速度；平移自由（齿轮只约束转动）。

## 3. 数据与协议

* `Mate` 目前是「两端 (a, b) + 数值」的二元结构，**装不下比例的多成员**。
  不要硬塞：新建独立的持久化实体（建议 `RatioGroup` / `GearMate`），各自有 id、参与结构、
  成员规则与参数；NBT 与网络都仿 `MateData` / `MateNetworking` 的写法各开一份。
* 树状图挂载（`ModelUi`）：比例组/齿轮按「参与了哪个模型」出现在各模型节点下的**配合**分支里，
  与标准配合并列（跨模型的组在两个模型下都出现，与既定约定一致）。
* 左侧编辑区：比例组显示成员列表 + 每行 k 值输入框；齿轮显示齿数比、反转复选框、四条轴的名称。

## 4. 离线可验证的部分（checker）

这部分**不进世界也能断言**，必须加进 `tools/MateFramesCheck.java`：

1. **比例不变式**：给定一组初始距离与 k，构造任意 `d_1`，断言算出的各 `d_i` 与目标相对误差 < 1e-9；
   且 `k_i` 是「按初始状态算出来的」（换一组初始距离，k 应随之改变）。
2. **比例退化保护**：`d_1⁰ = 0` 时不得产生 inf/NaN。
3. **齿轮不变式**：对任意 `θ_A` 序列，断言 `(θ_B − θ_B0) / (θ_A − θ_A0) = −ratio`（数值稳定），
   反转开关等价于 `ratio` 取反；`z_B = 0` 或齿数比非法时必须有明确拒绝路径（不产生 NaN）。
4. **角度环绕**：跨 ±180° 时从动角必须走最短路径（断言不出现「转了一整圈」的跳变）。

这些断言与既有的 4408 条一起跑，是这两类配合唯一能在没有游戏客户端时钉死的正确性部分。

## 5. 与「幽灵物体只传递力」原则的一致性

标准配合用**虚拟夹具**传递力；比例/齿轮用**速度级辅助**传递运动。两者都不给幽灵物体
质量与碰撞，都不允许「一边锁一边限」的自相矛盾：
* 比例：只有从动结构的**测量轴位置**被改写，其它自由度一概不碰（否则会与其它配合打架）；
* 齿轮：只改写**绕轴角**，平移与其它两轴转动一概不碰。

这条「只碰自己那一个自由度」的纪律必须写进实现处的注释，否则后面很容易被改坏。
